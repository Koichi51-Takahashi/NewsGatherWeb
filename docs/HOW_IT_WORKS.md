# NewsGatherWeb の仕組み解説

## 1. この資料について

このサイト（NewsGatherWeb）は、NHKニュースと時事通信の新着見出しを自動的に集めてきて、Webページとして公開するものです。

自分のパソコンを起動していなくても、インターネット上の「無料の仕組み」を使って、決まった時刻に自動的にニュースを取得し、サイトを最新の状態に更新し続けています。

この資料は、以下の2つの目的で書いています。

- **自分自身の学習用**：今回のサイト構築で使った技術（GitHub、GitHub Actions、GitHub Pagesなど）は普段馴染みのないものばかりだったので、後から読み返して「なるほど、こういう仕組みだったのか」と理解できるようにする
- **同僚への説明用**：同じ内容をそのまま見せれば、仕組みの概要が伝わるようにする

専門用語やカタカナ語・英語の略語が出てくる場合は、初めて登場するときに必ず「（　）」で簡単な補足を入れています。読み飛ばさずに、その都度確認しながら読み進めてください。

## 2. 全体像（3行でつかむ）

まず、細かい話に入る前に、全体の流れをざっくり3行で表すとこうなります。

> **決まった時刻に**、**外部の「目覚まし時計」サービス**が、
> **GitHubに向けて「今すぐ動いて」と指示を送り**、
> **GitHub上のロボット（自動作業員）がNHK・時事通信のニュースを取りに行って、このサイトの内容を最新のものに書き換える**

これを図にすると、以下のような流れになります。

```mermaid
flowchart LR
    Z["決まった時刻になる<br>（1日3回）"] --> A["外部の定期実行サービス<br>（cron-job.org）が<br>GitHubに指示を送る"]
    A --> B["GitHub Actions が<br>作業用の仮想パソコンを用意する"]
    B --> C["Pythonのプログラムが<br>NHK・時事通信のサイトへ<br>ニュースを取りに行く"]
    C --> D["取得した見出し・記事を<br>Webページ（HTML）の形に<br>まとめ直す"]
    D --> E["GitHub Pages が<br>そのページを公開する"]
    E --> F["コーイチさんが<br>ブラウザでサイトを見る"]
```

ポイントは、**このサイトはコーイチさんのパソコンが起動していなくても動く**という点です。すべての作業は「インターネット上の借り物のパソコン」（後述するGitHub Actions）の中で行われます。「決まった時刻になったことをどこが検知するか」については、当初はGitHub自身の機能に任せていましたが、後述（7章）の理由により、現在は外部の専用サービスに検知・声かけの役目を任せています。

## 3. 登場する用語の解説

これから説明に出てくる言葉を、先にまとめて解説しておきます。一つずつは難しくないので、身構えなくて大丈夫です。

| 用語 | 一言でいうと | もう少し詳しく |
|---|---|---|
| **GitHub**（ギットハブ） | プログラムの置き場所を貸してくれるWebサービス | 世界中のプログラマーが、自分の作ったプログラムを保存・共有するために使うサービス。今回はここに「ニュースを取ってくるプログラム」を保存している |
| **リポジトリ**（repository） | プログラム一式を入れておく「フォルダ」のようなもの | GitHub上に作る、プログラムファイル一式の保管場所。今回の`NewsGatherWeb`がまさにこれ |
| **GitHub Actions**（ギットハブ・アクションズ） | GitHubが用意してくれる「自動作業員」 | 「決まった時刻になったら、このプログラムを実行してね」と指示しておくと、GitHubが一時的にパソコン（正確には「仮想マシン」＝ソフトウェアで作られた仮のパソコン）を用意し、指示通りに作業して、終わったら片付けてくれるサービス。無料の範囲で使える |
| **ワークフロー**（workflow） | 自動作業員（GitHub Actions）への「作業手順書」 | 「何時に」「何をする」を書いた設定ファイル。今回は`.github/workflows/update-news.yml`というファイルがこれにあたる |
| **YAML**（ヤムル） | 設定を書くための文章の書き方（ルール） | プログラムのコードほど堅苦しくなく、人間にも読みやすい形式で設定を書くためのルール。ワークフローの作業手順書はこの形式で書く |
| **cron**（クロン） | 「毎日この時刻に」を指定する昔からある書き方 | 「何分・何時・何日・何月・何曜日に実行するか」を5つの数字や記号で表す、コンピューターの世界で古くから使われている定期実行の指定方法。GitHub Actionsもこの書き方を使っている（ただし本文中で後述する理由により、現在GitHub側のこの機能自体は使っていない） |
| **GitHub Pages**（ギットハブ・ページズ） | GitHubが無料でくれる「ホームページの置き場所」 | リポジトリの中にHTMLファイル（Webページの中身）を置いておくと、それをインターネット上に公開してくれるサービス。今回のサイトのURL（`https://Koichi51-Takahashi.github.io/NewsGatherWeb/`）はこの仕組みで公開されている |
| **スクレイピング**（scraping） | Webページから必要な情報だけを抜き出す作業 | 人間がニュースサイトを見て「これが見出し、これが時刻」と読み取るのと同じことを、プログラムに自動でやらせること |
| **UTC**（協定世界時） | 世界共通の「基準となる時刻」 | 日本時間は「UTC＋9時間」。GitHubの自動作業員はデフォルトでUTCで動いているため、何もしないと日本時間と9時間ずれる（→7章で詳しく） |
| **API**（エーピーアイ） | プログラム同士が会話するための「窓口」 | 人間がWebサイトの画面をマウスで操作する代わりに、プログラムが直接「これをやってください」と依頼できる窓口のこと。今回は外部の定期実行サービスが、この窓口を通じてGitHubに指示を送っている |
| **アクセストークン**（access token） | 特定の作業だけを許可する「合鍵」 | GitHubへのログインパスワードの代わりに使う、権限を絞った鍵。今回は「このリポジトリの自動実行だけ」を許可したトークンを発行し、外部の定期実行サービスに預けている |
| **cron-job.org**（クロンジョブ・ドットオルグ） | 正確な時刻に指示を送ってくれる、外部の「目覚まし時計」サービス | 決まった時刻になったら、インターネット経由でGitHubに「これを実行してください」という指示（API呼び出し）を送ってくれる無料サービス。GitHub自身の定期実行機能は混雑により遅れることが分かったため、こちらに切り替えた（→7章で詳しく） |
| **workflow_dispatch**（ワークフロー・ディスパッチ） | 「今すぐ実行して」という指示を受け取るための窓口 | GitHub Actionsの中で、手動のボタン操作や、外部からのAPI経由の指示によって、その場で作業を始めるための仕組み |

## 4. なぜこの仕組みが必要なのか

### 4-1. 元々あったローカル版との違い

実は、このサイトを作る前から、コーイチさんの自分のパソコン（Windows）の中だけで動く「NewsGather」という同じ機能のプログラムがすでにありました。そちらは、Windowsの「タスクスケジューラ」（決まった時刻にプログラムを自動実行してくれるWindowsの標準機能）を使って、1日3回ニュースを取得し、パソコンの中にWebページのファイルを作っていました。

ただしこの方法には弱点があり、**自分のパソコンの電源が入っていて、ログインしている時間帯にしか動かない**という制約がありました。また、そのファイルを見るにも自分のパソコンからしかアクセスできません。

そこで今回、同じ仕組みを「インターネット上」で動かすことで、パソコンの電源に関係なく、かつどの端末からでも見られるようにしたのが、このNewsGatherWebです。

### 4-2. GitHub Pagesだけでは動かない理由

ここが今回のシステム構築で一番のポイントです。

GitHub Pagesは、あくまで**「すでに出来上がっているWebページのファイルを置いて、みんなに見せる場所」**でしかありません。プログラムを実行する機能は持っていません。

一方で、ニュースを取ってくる作業（スクレイピング）は、NHKや時事通信のWebサイトにアクセスして、その中身を解析するという「プログラムの実行」が必要な作業です。GitHub Pages単体では、この作業はできません。

また、「ではブラウザ上のJavaScript（Webページ自体にプログラムを埋め込む方法）で、ページを開いた人のブラウザから直接ニュースサイトを取りに行けばいいのでは？」と思うかもしれませんが、これも通常はできません。Webブラウザには**CORS（コルス。他のサイトへの勝手なアクセスを制限するセキュリティの仕組み）**という制約があり、あるサイトのページから別のサイトのデータを自由に取りに行くことはブロックされるのが基本だからです。

そこで、「プログラムを実行する部分」と「できあがったページを公開する部分」を、以下のように役割分担しています。

- **プログラムを実行する部分** → GitHub Actions（自動作業員）が担当
- **できあがったページを公開する部分** → GitHub Pages が担当

## 5. 処理の流れ（時系列）

実際に何が起きているか、時間の流れに沿って説明します。

1. **決まった時刻になる**（1日3回：8:45・11:57・17:45、日本時間）
2. **外部の定期実行サービス（cron-job.org）が、GitHubに向けて「今すぐ実行してください」という指示（API呼び出し）を送る**
3. **GitHub Actionsが起動する**。GitHubが一時的に仮想の作業用パソコン（Ubuntu〔ウブントゥ〕というLinux系OSが動くもの）を用意する
4. その仮想パソコンの中で、リポジトリに保存してあるPythonのプログラム一式が展開される
5. **プログラムが実行される**（`python main.py --quiet`というコマンド）
   - NHKの新着一覧ページ、時事通信の新着一覧ページに順番にアクセスする
   - 直近12時間以内に出た記事だけを見出しとして抜き出す
   - それぞれの記事の本文（またはNHKの場合は要約文）も取得する
6. 取得した内容をもとに、**Webページ（HTMLファイル）を組み立てる**
   - 縦並び版（`index.html`）
   - 横並び版（`report2.html`）
   - 記事ごとの本文ページ（`articles`フォルダの中の各ファイル）
7. 出来上がったファイル一式を**GitHub Pagesに渡して公開する**
8. **仮想パソコンは役目を終えて片付けられる**（毎回使い捨てで、次回はまた新しく用意される）
9. コーイチさんがブラウザでサイトを開くと、最新の内容が表示される

## 6. ファイルの役割一覧

このプログラムは、役割ごとに複数のファイルに分かれています。

| ファイル | 役割 |
|---|---|
| `main.py` | 全体の実行の入り口。「取得→絞り込み→表示」の一連の流れを取りまとめる |
| `config.py` | どのサイト（NHK・時事通信）を、どうやって取得するかの設定一覧 |
| `fetcher.py` | Webページの中身（HTML）をインターネット経由で取得する処理 |
| `parsers.py` | 取得したHTMLの中から、見出し・時刻・リンクだけを抜き出す処理 |
| `timeutil.py` | 「直近12時間以内かどうか」を判定する時刻計算の処理 |
| `article.py` | 記事本文（またはNHKの場合は要約文）を取得する処理 |
| `report.py` | 取得結果を実際のWebページ（HTML）の形に組み立てて保存する処理 |
| `.github/workflows/update-news.yml` | GitHub Actionsへの「作業手順書」。いつ・何を実行するかが書いてある |

これらのうち、`main.py`から`report.py`までの7つはPythonのプログラムで、`update-news.yml`だけが「GitHub Actionsへの指示書」（YAML形式）という違いがあります。

## 7. 実際に起きたトラブルの実例（教材として）

### 7-1. 取得日時が9時間ずれていた問題

サイトを公開した直後、「取得日時：2026年07月15日 06:46」のように、**実際の時刻より9時間前の時刻**が表示されるという問題が起きました。この実例は、クラウドサービスを使う上での典型的な注意点なので、教材として残しておきます。

#### 何が起きていたか

GitHub Actionsが用意する仮想パソコンは、標準では**UTC（協定世界時、世界共通の基準時刻）**で動いています。日本時間はこのUTCより9時間進んでいる（`UTC＋9`）ため、何も指定しないと、プログラムが記録する時刻がすべて9時間ずれてしまいます。

これは自分のパソコン（Windows）で動かしていたときには起きなかった問題です。自分のパソコンはあらかじめ「日本時間」に設定されているためです。しかしGitHub Actionsの仮想パソコンは、世界中の誰でも使う共通のサービスなので、特定の国の時間には最初から合わせられていません。

#### どう直したか

最初はワークフロー（作業手順書）の中で「このパソコンのタイムゾーン（どの地域の時刻を使うか）を日本時間にしてください」という指定（`TZ: Asia/Tokyo`）を追加しました。ところが、これだけではPythonのプログラム内部の時刻計算までは反映されず、ズレは直りませんでした。

最終的に、`main.py`の中で「時刻を取得するときは、必ずUTCより9時間進んだ時刻にする」という指定を、プログラムのコードそのものに直接書き加えることで解決しました。

#### この実例からの教訓

- クラウド上で動くプログラムは、**自分のパソコンとは前提となる時刻・地域設定が違う**ことがある
- 「OS（パソコン全体）の設定」を変えるだけでは、プログラムの中身まで自動的には反映されないことがある
- 想定と違う結果が出たときは、「そもそも実行されている場所（環境）の前提が違うのでは？」と疑ってみることが大事

### 7-2. 「決まった時刻からズレる」問題と、外部サービスへの切り替え

サイト運用開始後、更新時刻を確認していたところ、狙った時刻（8:45・11:57・17:45 JST）より**常に1〜2.7時間ほど遅れて**更新されていることが分かりました。

#### 何が起きていたか

GitHub Actionsの「決まった時刻に実行する」機能（`schedule`）は、GitHub全体の混雑状況に左右されるため、必ずしも指定した時刻ぴったりには実行されません。最初は設定時刻を早める（前倒しする）対応を試しましたが、5日間・26回分の実行記録を数値で調べたところ、**前倒ししても実際にサイトが更新される時刻はほとんど変わらない**ことが分かりました。特定の時間帯そのものが混雑しやすく、そこに引きずられて実行されている、という状態だったためです。

#### どう直したか

一方で、画面の「Run workflow」ボタンを押して手動実行したときは、ほぼ待ち時間なく即座に動いていました。そこで、GitHub自身の「決まった時刻に実行する」機能を使うのをやめ、**外部の定期実行サービス（cron-job.org）から、正確な時刻にGitHubへ直接指示を送る**方式に切り替えました。GitHub内部の混雑した順番待ちの列に並ぶのではなく、外部から「今すぐお願いします」と直接声をかける形にすることで、待たされにくくしています。

#### この実例からの教訓

- 無料で使える自動化の仕組みは、便利な半面「必ず指定時刻に実行される」とは限らない
- 「時刻を前倒しする」ような対症療法では直らない問題もあり、実行記録を数値で確認して初めて実態が分かることがある
- 一つの仕組み（GitHub）の中だけで解決しようとせず、外部の別の仕組みと組み合わせることで解決できる場合がある

## 8. 運用方法

### 手動で今すぐ更新したいとき

1. リポジトリのページ（`https://github.com/Koichi51-Takahashi/NewsGatherWeb`）を開く
2. 上部の **Actions** タブをクリック
3. 左側の **Update News** を選択
4. **Run workflow** ボタン → もう一度 **Run workflow** をクリック
5. 数十秒待つと、サイトの内容が更新される

### 一時的にサイトを止めたいとき

サイトを一時的に非公開にしたい場合、以下の2つをセットで行うのが望ましいです（片方だけだと、裏側の自動更新だけが無駄に動き続けてしまうため）。

1. **サイトの公開を止める**：リポジトリの **Settings** → **Pages** → **Build and deployment** → **Source** の設定を変更する
2. **自動更新も止める**：cron-job.org側で、3つのジョブを一時停止（無効化）する

どちらも元に戻せば、いつでも再開できます。

## 9. リスク・注意点

- **時事通信の取得がブロックされる可能性**：時事通信のニュース一覧は、`textise.net`という別のサービスを経由して取得しています。このサービスはCloudflare（不正アクセス対策サービス）によるボット（自動プログラム）対策をしており、GitHub Actions側のアクセス元によっては、今後ブロックされる可能性があります。もし時事通信だけ取得できなくなった場合は、NHKと同じ「直接取得」方式に切り替える対応が必要です
- **外部サービス（cron-job.org）への依存**：定期実行の起点を、GitHubとは別の無料の外部サービスに委ねています。GitHub自身の`schedule`機能にあった遅延は解消できましたが、代わりに「そのサービス自体が停止・障害を起こしたら自動更新も止まる」という、別の依存先が増えたことになります
- **GitHubアクセストークンの有効期限管理が必要**：cron-job.orgに預けているトークンには90日の有効期限があります。期限が切れると自動更新が止まるため、期限が近づいたら再発行・再設定する必要があります（GitHubからの通知メールに加えて、Claude Codeによるリマインドも設定済み）
- **キャッシュ（一時保存）を行っていない**：元のローカル版は、一度取得した記事を48時間保存して使い回していましたが、このGitHub Pages版では、実行のたびにすべての記事を新規に取得し直しています（クラウド上の作業環境は毎回使い捨てになるため、保存の仕組みを作らずシンプルにする方針にしました）
